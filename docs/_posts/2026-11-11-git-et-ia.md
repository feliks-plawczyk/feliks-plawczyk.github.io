Un assistant IA peut écrire en quelques minutes ce qui prenait une journée. C'est une bonne nouvelle, à condition de pouvoir **contrôler** ce qu'il a fait : savoir ce qui a changé, revenir en arrière et travailler à plusieurs. C'est exactement le métier de Git. Avec l'IA, il passe du statut d'outil de développeur à celui de socle.

<!--more-->

## Le cycle de développement a changé

Une façon de plus en plus courante de travailler avec un agent IA suit quatre phases : **spécifier** ce qu'on veut, **planifier** les étapes, **implémenter**, puis **relire**. Des collections de *skills*, c'est-à-dire des consignes réutilisables qu'on donne à l'agent, encadrent chaque phase. Le dépôt [`addyosmani/agent-skills`](https://github.com/addyosmani/agent-skills) en est un exemple : il propose des commandes comme `/spec`, `/plan`, `/build`, `/test`, `/review` et `/ship`.

Chaque phase **produit des fichiers** : une spécification, un plan de tâches, du code, des tests. Le même dépôt recommande d'ailleurs de versionner la spécification avec le code : un document qui guide le travail de l'IA doit avoir un historique, comme le reste.

Ce blog est construit ainsi. Chaque article commence par une spec, dans le dossier `specs/` du dépôt, puis vient le texte. C'est aussi ma façon de travailler en mission depuis plusieurs mois.

## Ce que Git apporte face à l'IA

Les idées de [l'article d'introduction]({{ site.baseurl }}/blog/20261109-vcs) prennent une valeur nouvelle. Voici cinq apports de Git.

1. **Annuler :** un agent peut modifier dix fichiers d'un coup, parfois dans le mauvais sens. Avec Git, un retour à l'état précédent prend une commande, sans rien perdre.
2. **Relire :** Git montre précisément ce qui a changé, ligne par ligne (le *diff*). La phase de revue consiste justement à lire ce diff avant d'accepter le travail de l'IA.
3. **Expérimenter :** on laisse l'agent tenter une idée dans une **branche**, sans toucher à la version de référence. Si ça échoue, on supprime la branche.
4. **Collaborer :** une demande de fusion (*pull request* ou *merge request*) permet à un collègue de relire avant l'intégration, que le travail vienne d'un humain, d'une IA ou des deux. Les plateformes comme GitHub et GitLab, présentées dans [Git, GitLab, GitHub : qui fait quoi ?]({{ site.baseurl }}/git-gitlab-github), s'occupent de cette étape.
5. **Tracer :** chaque changement garde son auteur, sa date et son explication. Le même dépôt demande d'ailleurs à son mode automatique de **committer chaque tâche séparément** : l'historique se lit comme le journal du travail.

## Et si on ne code pas ?

Des outils comme [Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork) s'adressent à des personnes qui ne sont pas développeurs : ils travaillent directement sur des fichiers et des dossiers de votre ordinateur. Le principe est le même : dès qu'un agent peut **modifier ou supprimer** vos fichiers, il faut un filet de sécurité que vous maîtrisez, indépendant de l'outil.

Git le fournit : sauvegarde, restauration de n'importe quelle version, travail à plusieurs. Une limite à connaître : Git suit très bien le **texte, le Markdown et le code**, mais mal les fichiers **Word ou Excel**. Il les conserve, sans pouvoir montrer ce qui a changé à l'intérieur. Si vous travaillez avec un agent, privilégiez des formats texte.

## Trois réflexes pour démarrer

1. **Enregistrer avant de lancer l'agent.** Un `commit` propre vous donne un point de retour garanti.
2. **Une branche par tâche.** Elle isole le travail de l'IA de votre version de référence.
3. **Relire le diff avant d'accepter.** C'est votre revue, et le meilleur moyen de rester responsable de ce que vous publiez.

```bash
git status                    # l'état de départ est propre ?
git switch -c feat/ma-tache   # une branche pour cette tâche
# ... l'agent travaille ...
git diff                      # qu'est-ce qui a changé ?
git add -A && git commit -m "feat: ma tâche"
```

## À retenir

* L'IA accélère la production, donc le besoin de **contrôle** augmente.
* Le cycle spécifier, planifier, implémenter, relire s'appuie sur des fichiers : ils doivent être **versionnés**.
* Git apporte l'annulation, la relecture, l'expérimentation, la collaboration et la traçabilité.
* Même sans écrire de code, un agent qui touche à vos fichiers justifie d'utiliser Git.
